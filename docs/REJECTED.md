# 已否定方案

这里只记录有证据、代价较高且未来容易被重复提出的否定决策。

## Companion 直接依赖 OpenClaw 运行时目录

**结论：拒绝。** OpenClaw 是生产行为基线和独立宿主，不是 Companion 的长期 SDK。共享能力应抽成版本化、宿主无关的 package，由两个宿主固定消费同一制品；禁止深层相对路径、已部署用户目录和 CLI 文本合同。

## 把单一模型或 DeepSeek Harness 设为稳定核心

**结论：拒绝。** Harness 与模型是可替换适配器。真实模型分数受运行配置、提示、工具命名和评分协议影响，只进入报告，不替代确定性合同与权限门禁。

## 为作品集提前引入 SQLite、向量库、RAG、MCP 或多用户云服务

**结论：拒绝，等待触发条件。** 只有跨进程事务、可量化语义缺口、真实外部消费者或明确产品范围变化出现时，才重新评估对应技术。

## 两个宿主长期维护两套同名业务

**结论：拒绝。** 文档同步不能保证事实、错误、缓存和状态机一致。迁移必须经过共享合同、shadow 对比、单写者停切与旧实现删除。

## 把完整发布链和跨宿主迁移作为桌面原型前置条件

**2026-09-03 结论：调整顺序。** 原计划要求先完成 P1.1/P1.2，再推进原生交互；但当前 Agent 仍只有文字结果、切页丢失会话、模型说明与实际选择不一致。维护者明确当前目标是搭建原型并逐项对齐现有助手功能，因此从 D0 对照表和 D1 完整流程起步，立即推进后续功能，D2 体验工作随功能进行。安装发布在需要分发时进入，跨宿主迁移在需要共同消费稳定实现时进入。既有测试与只读边界保留，原型期间暂存的重复实现不阻塞桌面开发。

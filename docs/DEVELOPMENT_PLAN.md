# Warframe Companion 开发总纲

> 状态：执行基线（living document）
> 制定日期：2026-08-29
> 当前代码基线：`main=70f4302`；候选分支 `deepseek/eval-prod-isomorphism=b602204`
> 适用范围：`warframe-companion` 产品化、共享核心迁移和与 OpenClaw 的宿主边界
> 维护方式：完成一个可独立验收的切片后更新状态、证据和下一入口；估时只用于排序，不作为完成证明

## 1. 最终方向

把 Warframe Companion 做成 Windows 本地优先的个人 Agent 主机：桌面 UI 与 Agent Harness 负责交互、模型适配和呈现；宿主无关的确定性核心负责事实、证据、错误、实体和业务决策；本地 Channel Gateway 负责绑定和承载可选远程频道。QQ/OpenClaw 是现有第一条远程通道，后续可按真实需求增加飞书、微信或其他社媒适配器。

两条产品线的关系是：

- 复用同一个可版本化、可测试、可发布的确定性核心，不各写一套同名业务。
- 移植 OpenClaw 已验证的工程纪律和生产语义，不把 OpenClaw 运行时目录直接变成 Companion 的源码依赖。
- OpenClaw 在迁移期是生产行为基线和验收参照；共享包完成双宿主切换后，发布的共享包才是唯一可执行事实源。
- 桌面端成为主要产品入口；远程频道保持可选查询与提醒入口，不承担桌面产品契约，也不得各自复制业务实现。

## 2. 对现有建议的判断

### 2.1 接受

- 本地优先、确定性优先、模型不写事实/身份/状态、Warframe 与账号集成只读。
- 先补 CI、发布、验收分层和仓库治理，再扩功能。
- 一个切片同时交付工具契约、业务实现、评估、文档和故障语义。
- 状态型能力迁移时只允许一个宿主写，使用明确的 shadow、停切和回滚流程。
- 可复现的契约与事实投影进入门禁；真实模型质量、延迟和成本进入报告。
- SQLite、RAG、长期模型记忆、内部 MCP 等能力只在真实需求达到阈值后引入。

### 2.2 修正

1. **共享核心不等于 OpenClaw 仓库。** OpenClaw 当前 Skill 是成熟生产实现，但带有运行时目录、QQ 编排、CJS/ESM 和部署布局约束，不应由桌面端按路径直接导入。应抽成带公共 exports、版本号、lockfile 和合同测试的共享包。
2. **先建 CI，再合并候选分支。** 当前仓库没有 `.github`。不能要求一个尚不存在的检查阻断现有 PR；先从 `main` 用小 PR 建最小 CI，再审查 `deepseek/eval-prod-isomorphism` 的四个提交，必要时拆分或重放，不能预设整支必然合并。
3. **已有能力不重新列为待开发。** Companion 已有 `market.query`、`drops.search`、桌面壳、健康页、Agent Harness、OpenAI-compatible adapter、工具结果回送和 41 条合成评估。下一步是落地主线、去重和产品验收，不是重写。
4. **不以工具数量为目标。** “8–12 个工具”不是架构指标。工具面按完整用户任务收敛；能用一个高层用例表达的，不拆成多个模型可见低层工具。
5. **纵深能力前置最小骨架、按证据扩展。** trace 和故障注入的最小版本应在第一个跨宿主切片出现；知识管道、复杂上下文、模型路由和 MCP 则等真实缺陷或量化收益触发。
6. **不承诺固定周数。** 跨仓库去重、Windows 安装包和状态停切的风险差异很大。计划使用切片、入口条件和退出条件管理，而不是用日历掩盖不确定性。

### 2.3 明确不采用

- Companion 直接 import 已部署 OpenClaw Skill 路径或调用其 CLI 文本作为长期应用接口。
- 两个宿主各自维护 market、worldstate、实体解析、错误合同或状态机，再靠文档要求“保持一致”。
- 将 DeepSeek Harness、OpenClaw 或任何单一模型/provider 设为桌面稳定链路的强依赖。
- 每日 AI 维护任务直接进入发布门禁；确定性维护检查可定时运行，模型维护只能生成待审报告且默认不外发。
- 为作品集观感提前加入向量库、数据库、MCP、功能旗标平台、云服务或多用户系统。

## 3. 目标边界

```text
Windows Desktop / Remote Channels
        │
        ▼
宿主适配层
  - Desktop：IPC、React、模型 profile、Agent 事件、桌面配置
  - Channel Gateway：绑定、可信身份、入站归一、Outbox、能力协商
  - Adapters：OpenClaw/QQ bridge、飞书、微信、其他社媒
        │
        ▼
共享应用接口
  - 高层用例注册表
  - CapabilityPolicy 输入
  - ToolResult / Evidence / UserError
        │
        ▼
共享确定性核心
  - 实体解析
  - 公共数据源与降级
  - Facts → Decision
  - AccountSnapshot 白名单投影
  - Store / Monitor / Outbox 的宿主无关合同
        │
        ▼
外部只读数据源与本机只读快照
```

### 3.1 共享核心拥有

- 稳定实体 ID、名称/slug/uniqueName 映射与来源。
- 请求/结果 schema、证据信封、新鲜度、错误类别和重试语义。
- 公共数据获取、校验、缓存、降级和事实归一化。
- 与渠道无关的推荐/判断规则及 `Facts → Decision`。
- 版本化、白名单、脱敏的个人快照投影。
- 状态存储、调度、Outbox 的接口与幂等规则；具体路径和投递器由宿主注入。

### 3.2 Companion 拥有

- Electron/React UI、preload IPC、本机配置和安装体验。
- `ModelProfile`、`ModelAdapter`、Agent loop、事件、取消、超时和 trace。
- 桌面原生卡片、可访问性与交互。
- 对共享高层用例的桌面适配，不复制业务实现。

### 3.3 Channel Gateway 与适配器拥有

- 频道连接生命周期、入站去重、速率限制、重连和健康状态。
- 由适配器从供应商事件生成可信频道/会话/发送者身份；用户文本不能声明这些字段。
- 本地审批的频道绑定、撤销和群聊范围；模型不能发起、批准或修改绑定。
- 确定性短命令的宿主拦截，但执行进入共享高层用例。
- 按频道能力选择原生卡片、按钮、Markdown、文字或图片回退。
- Outbox、投递回执和重试；供应商接受不伪称用户已经看到。
- OpenClaw/QQ 在迁移期可继续作为独立 bridge；是否改为 Companion 直连 QQ 由可量化收益决定，不为“统一外观”重写成熟链路。
- 生产状态的当前写入责任，直到某一状态域完成显式停切。

### 3.4 禁止依赖

- 禁止跨仓库深层相对路径导入、复制脚本或依赖已部署用户目录。
- 禁止以 CLI stdout、图片或自然语言作为共享业务合同。
- 共享包只能通过声明的 package exports 使用；消费者固定精确版本和完整性证据。
- 破坏性合同变更必须升主版本；迁移期至少保留一个兼容窗口。

### 3.5 原生交互呈现

桌面端不把 QQ PNG 或模型生成的 Markdown 当作主要结果界面。工具执行完成后，Agent 事件流同时交付可渲染的类型化结果；React 根据结果类型挂载原生组件，模型文字只负责解释，不能成为按钮的数据源。

- Market 结果使用可复用的 `MarketResultCard`，同时出现在独立市场页和 Agent 对话中。
- 卖家列表支持键盘可达的上一页/下一页、买卖方向和在线状态筛选；翻页是本地确定性 UI 行为，不重新调用模型。
- 每个卖单可提供“预览私聊文本 → 复制到剪贴板”。文本只从已校验的物品、等级、价格和当前行卖家生成，不解析模型回答。
- 复制属于用户明确触发的本地操作：不自动打开游戏、不自动发送聊天、不下单、不挂单，也不创建愿望状态。
- `evidence.expiresAt` 到期后禁用复制并要求刷新；刷新后的订单变化必须重新选择，不能把旧卖家/旧价格静默复制。
- 真实卖家名只在当前结果组件和用户剪贴板中短暂出现，不进入 AgentTrace、日志、遥测、持久化上下文、截图夹具或 eval。
- 初版在一次有界订单快照内分页；只有真实数据量证明必要时才新增游标服务，且该内部 UI 能力不自动暴露为新的模型工具。

### 3.6 多频道合同

Companion 自己拥有频道合同，但不建设通用社媒自动化平台。稳定最小面包括：

- `InboundEnvelope`：供应商消息 ID、频道、会话、可信 actor、接收时间、文本/附件和回复关系。
- `ChannelCapabilities`：文字、Markdown、图片、文件、原生卡片、按钮、编辑/撤回和最大尺寸；未知能力一律按最小文字回退。
- `OutboundMessage`：语义化内容 part、可选交互意图和无障碍文字回退，不直接携带某供应商 JSON。
- `DeliveryReceipt`：accepted/failed/unknown、稳定错误类别、是否可重试和供应商回执引用；不得保存原始错误正文。
- `ChannelAdapter`：connect/disconnect/health/send 与规范化 inbound event；业务核心看不到 webhook、长连接或轮询细节。

身份绑定只允许在本地管理界面启动和批准：使用短 TTL、单次使用的挑战码，把适配器提供的稳定外部身份映射到本地主体；绑定记录可查看、可撤销、按私聊/群聊范围授权。令牌只经环境变量引用或宿主安全凭据存储提供，不写入普通 JSON、日志或模型上下文。

远程频道生命周期不依赖某个 React 窗口是否打开。初版可由托盘常驻的本地 Gateway 承载；只有用户明确需要开机自启和无人值守时才评估 Windows 服务。每个新频道在实现前重新核对其官方 API、权限、审核、速率限制和数据保留要求，不凭旧认知假设可用性。

## 4. 当前基线

### 已实现

- `market.query` 契约、真实只读适配器、证据/错误与桌面原生卡。
- `drops.search` 许可明确的 WFCD 快照、源年龄门禁、替代源对照和本地索引。
- Companion 自有 Agent Harness、离线 profile、OpenAI-compatible adapter、SSE、取消、工具结果回送和稳定终态。
- `account.snapshot` 的权限/脱敏尖峰；生产数据服务尚未接入。
- 41 条合成/脱敏评估和确定性 runner。
- Electron 开发打包可完成；Windows/Node 22 CI、生产依赖审计和公开仓库合同已建立。当前还没有正式 `make`/安装验收或 GitHub Release 自动化。

### 已审查的候选分支

`deepseek/eval-prod-isomorphism` 的四个能力提交已逐项重放并纳入主线候选：

1. 生产与 eval 事实投影同构。
2. adapter 版本与 token/finish reason trace。
3. DeepSeek wire 工具名和 thinking-mode 回送兼容。
4. `account.snapshot` 权限尖峰。

审查发现个人快照的文本关键词门禁可被模型直接选择工具绕过，已把主人身份与频道授权下沉到 `account.snapshot` 实际执行点，并加入回归测试。根级 build/test/eval 与 GitHub CI 仍只证明源码与 CI 层，不替代安装包或实机验收。

## 5. 执行路线

每个阶段只规定顺序和门槛。实际工作以一个可独立验收的切片为单位；未满足退出条件不得跨阶段宣称完成。

### Phase 0：主线与工程自证

#### P0.1 最小 CI

状态：已实现；Windows/Node 22 的干净 runner 已通过，公开后将该检查设为 `main` 必需检查。

从 `main` 建独立小 PR，加入：

- Windows + Node 22 的 `npm ci`、根级 build、根级 test。
- eval 的确定性参考冒烟；不调用付费模型，不把模型分数设为门禁。
- lockfile、敏感字段/真实身份、生成报告漂移和文档链接检查。
- Action 固定完整 commit SHA；Dependabot 只更新明确允许的 npm 与 Actions 依赖。

退出条件：PR 检查可在干净 runner 重现本机结果，并被设为 `main` 必需检查。

#### P0.2 候选分支审查与落地

状态：已完成审查、最新主线重放与权限补强；以 PR CI 全绿和合并提交作为最终证据。

- 逐提交审查 `b000576..b602204`，重点检查生产/eval 同构、trace 隐私、thinking 内容不落盘、账号权限和大量生成报告的必要性。
- 在最新 `main` 上重放；若某提交不能独立解释或回滚，则拆分后再 PR。
- CI 全绿后合并；README、架构和基线数字与最终代码同位更新。

退出条件：`main` 含经审查的目标能力，分支无未解释差异；不要用“原分支已存在”替代 PR 评审。

#### P0.3 仓库治理

状态：已实现公开仓库模板、治理文档、Dependabot、生产依赖门禁与公开内容自检。

- PR/Issue 模板、CODEOWNERS、Dependabot、贡献流程。
- README 增加开发总纲和验收入口。
- 建立 `docs/ACCEPTANCE.md` 与 `docs/REJECTED.md`；前者定义四层验收，后者只记录有证据的重要否定决策。

### Phase 1：可安装产品与发布链

#### P1.1 版本和制品身份

- 明确预发布阶段的 SemVer；根 package、桌面 package、lockfile、CHANGELOG 同位更新。
- 构建产物记录源码 commit、版本、构建时间和内容哈希。
- `electron-forge make` 产出 Windows 安装制品；先允许明确标注的未签名预发布，不把未签名包描述为正式可信安装包。

#### P1.2 四层验收

| 层级 | 必需证据 | 不能声称 |
|---|---|---|
| 源码 | build/test/eval 门禁通过 | CI 已通过 |
| CI | 固定 commit 的必需检查全绿 | 安装包可用 |
| 打包 | `make`、安装/启动/卸载、构建身份核验 | 真实数据链全好 |
| 实机 | 健康页、真实只读 market 查询、来源/时间、故障降级 | 所有功能已迁移 |

#### P1.3 原生交互结果组件

- 将独立市场页现有订单列表抽成共享 `MarketResultCard`，Agent 对话按工具结果类型渲染同一组件，而不是只显示文本气泡。
- 一个有界快照内完成分页/筛选；页码、总数、快照时间与过期状态始终可见。
- 卖单行提供购买私聊文本预览与显式复制按钮；复制成功/失败有可访问反馈，过期结果必须先刷新。
- IPC/renderer 边界只接受经过合同校验的动作参数；剪贴板文本不进入模型、trace 或日志。
- 用合成卖家覆盖翻页、筛选、复制、过期、刷新后重选和键盘操作测试。

退出条件：用户在 Agent 对话中问价后能直接操作原生行情卡，并在不调用第二次模型、不发送任何聊天的前提下，预览和复制一条当前有效的购买私聊文本。

#### P1.4 Release

- tag 与 GitHub Release 同步；Release 附校验值、已知限制和验收层级。
- 发布工作流只消费已经通过审查的版本准备提交，不能在验证后临时改版本。
- 首个公开预发布至少完成安装、启动、升级/卸载恢复和真实只读市场查询。

### Phase 2：共享核心去重试点

#### P2.1 宿主无关合同

新增 ADR/合同文档并机器校验：

- 公共 exports、版本策略、运行时兼容矩阵。
- `ToolResult`、`Evidence`、`UserError`、实体身份和 CapabilityPolicy 输入。
- 依赖注入的 clock、HTTP、store、logger、transport；核心不得读取 QQ 或 Electron 全局状态。
- npm pack 制品和完整性校验；禁止 Git 深路径和已部署目录依赖。

共享包先在 Companion monorepo 内孵化；只有发布节奏或权限边界真实冲突时才拆独立仓库。OpenClaw 通过固定版本制品消费，不复制源码。

#### P2.2 Market 去重试点

Market 已在两条线存在，适合作为第一个去重证明：

1. 建立同一批合成 fixture 和故障矩阵，列出两边有意/无意语义差异。
2. 把最终请求、实体解析、订单/成交口径、错误和证据收敛到共享包。
3. Companion 先切换到共享包并保持现有 UI/eval 全绿。
4. OpenClaw 以 shadow 方式对同一请求比较旧/新事实，不改变 QQ 输出、不写状态。
5. 差异归零或完成书面裁决后，再让 OpenClaw adapter 切换；保留一版可回滚旧实现。
6. 删除第二套实现；只有删除完成，才能标记“唯一事实源”。

退出条件：两宿主固定同一共享包版本；合同、故障注入和至少一条真实只读烟测通过；没有运行时路径依赖。

#### P2.3 世界状态/裂缝

复用 OpenClaw 已验证的 R7 语义，作为第一个新能力：

- DE 官方完整状态优先；备用源按字段能力使用，不把部分镜像冒充全量状态。
- 来源、内容时间、抓取时间、字段 provider、完整性和 stale 分开表达。
- 可靠缓存只接受通过合同的完整快照；字段叠加结果不反向污染完整缓存。
- 覆盖 404/403/429/超时、坏 JSON、缺字段、过龄、源分歧和全源失败。
- Companion 用原生裂缝视图展示；OpenClaw 继续使用 QQ 呈现，但共享同一事实与决策。

#### P2.4 Channel Gateway 最小骨架

1. 定义 `InboundEnvelope`、`ChannelCapabilities`、`OutboundMessage`、`DeliveryReceipt` 和 `ChannelAdapter`，配套合成 test adapter。
2. 把桌面对话入口接到相同入站/权限/用例管线，但保留原生 UI 返回通道。
3. 实现本地绑定表、一次性挑战、撤销、私聊/群聊范围和敏感字段脱敏合同。
4. 建立托盘 Gateway 生命周期、adapter 健康页、Outbox 模拟投递和重启恢复测试。
5. 用 OpenClaw/QQ bridge 验证兼容边界；第一个新增真实频道只选一个，并依据届时官方接入条件和用户优先级决定。

退出条件：合成频道能完成“入站 → 可信身份 → 确定性路由/Agent → 共享用例 → Outbox → 模拟回执”，Gateway 重启不重复处理同一入站，也不会因模型输出改变绑定或投递目标。

### Phase 3：按风险迁移功能

建议顺序如下；每项仍是独立切片：

1. 遗物与获取路线：先公共只读事实，再个人库存增强。
2. 周常只读视图：周期边界、来源和新鲜度先统一。
3. 订阅/Outbox：先只读诊断，再 shadow 调度，再单写者停切。
4. 愿望单 + Market WebSocket：复用健康状态机、保护轮询、幂等与限流；不得双跑写状态。
5. AccountSnapshot：接真实本机只读适配器，只输出版本化白名单摘要；群聊和不可信会话在工具前拒绝。
6. 第二个真实远程频道：在 Channel Gateway 骨架稳定后只接一个，先完成查询与安全回退，再考虑提醒；不同时铺开飞书、微信和其他社媒。
7. 卡片与个人决策：事实/决策共享，桌面使用原生交互组件，各远程频道按能力使用原生卡片或图片/文字；不共享最终视觉产物。

### 状态型切片的强制停切协议

任何愿望、订阅、Outbox、调度或可变上下文迁移必须依次完成：

1. 固定旧 schema、路径、所有者和备份策略。
2. 新实现只读导入并做 shadow 比较，禁止投递和写回。
3. 验证幂等键、周期边界、锁、崩溃恢复和回滚。
4. 明确维护窗口；停止旧写者并确认租约/进程已退出。
5. 单次迁移，记录 schema 版本、条目计数和脱敏哈希。
6. 启用新写者；验证后仍只允许一个写者。
7. 回滚只恢复受管代码和兼容状态，不删除或重建用户数据。

### Phase 4：纵深能力

这些能力不按“技术栈完整度”排期，只在前置证据出现后进入切片：

- **最小 trace/E2E：** 第一个共享核心试点就记录本地脱敏 request/route/policy/source/decision/presentation；第一个状态型迁移前完成“入站 → 模拟通道”E2E 和故障注入。
- **结构化短时上下文：** 只有真实多轮任务出现重复澄清或实体丢失时引入；默认 15–30 分钟 TTL，只存解析实体、明确偏好和结果摘要。
- **知识管道：** 先收集两周无命中/漂移报告，再决定实体目录和窄语义包边界；不镜像完整 Wiki。
- **模型路由：** 有真实 token、延迟、成功率数据后比较确定性规则、轻模型和强模型；模型质量分只做报告。
- **MCP 导出：** 只有出现真实外部消费者时才把稳定高层用例作为能力发布；不把它当内部模块边界。
- **SQLite：** 仅在跨进程写竞争、跨实体事务或测得 JSON/内存方案越过预算时迁移。

## 6. 每个切片的 Definition of Done

一个切片至少同时满足：

1. 明确目标、非目标、数据/运行时/渠道影响和固定基线。
2. 稳定类型/Schema、未知字段拒绝、错误与证据语义完整。
3. 测试只用合成或脱敏数据；不包含 key、账号/QQ 标识、真实玩家、原始快照、响应体或本机日志。
4. 正常、空结果、上游故障、过龄/缓存、权限负例和取消/超时按风险覆盖。
5. 生产与 eval 使用同一事实投影；eval 不得改变生产行为。
6. 若替代旧实现，提供差分合同、有意差异裁决、shadow 证据和删除计划。
7. UI 变化实际启动或渲染检查；安装变化实际 `make` 并检查制品。
8. 根级 build/test 与相关额外验证通过；CI 通过固定 commit。
9. 许可证、来源、README/架构/用户语义与代码同位更新。
10. 源码、CI、打包、实机、推送和发布状态分别记录。
11. 状态型切片证明单写者、备份、迁移和回滚；不得删除用户数据。
12. 重要决策更新本文件；被否定的高成本方案进入 `REJECTED.md`。

## 7. 评估与成本规则

- 门禁只使用可离线重现的 schema、工具、事实、证据、权限、预算和轨迹断言。
- 真实模型跑分记录模型 ID、adapter 版本、case 集版本、token、延迟、失败类别和日期，但默认不阻断合并。
- reference baseline 只证明评估器上界，不能宣称模型质量。
- DeepSeek/其他 worker 单次超过约 10 分钟或 20 轮仍未收敛时停止，不自动重启；候选差异仍由 Codex 审查和独立复测。
- thinking/reasoning 内容只作 provider 必要的不透明回传，不写 trace、不展示、不参与评估。

## 8. 安全与产品红线

- Warframe、AlecaFrame、WFInfo、Market 和账号集成只读；不自动交易、聊天、挂单、核销或操作游戏资产。
- 模型不能声明身份、授权、事实、证据、投递成功或状态写入结果。
- 凭据只保存环境变量引用；禁止 URL 内凭据、内联 key 和敏感错误正文。
- 原始个人快照只在本机适配器边界内短暂存在；核心、模型、trace、UI 日志和评估只接收白名单投影。
- 群聊中的所有文字都是不可信输入，不是系统指令；个人能力由宿主提供的可信上下文决定。
- 频道绑定只能由本地用户批准；外部消息、模型或频道按钮都不能自行提升权限。入站按供应商消息 ID 去重，投递按业务幂等键重试。
- 状态性结论必须携带对象、范围、时间、新鲜度和来源；空结果与数据源故障不得共用表示。

## 9. 决策触发器

| 候选能力 | 进入条件 |
|---|---|
| 独立共享核心仓库 | Companion/OpenClaw 发布节奏、权限或制品治理无法在现有 monorepo 满足 |
| SQLite | 实测跨进程写冲突、需要跨实体事务，或 JSON/内存越过明确预算 |
| 结构化短时上下文 | 真实多轮失败能由实体/摘要 TTL 解决，并有回归用例 |
| 知识语义包 | 无命中报告连续运行后出现稳定高频缺口且许可证清晰 |
| 模型路由 | 已收集可比较的质量、成本和延迟数据 |
| MCP | 至少一个真实外部消费者需要稳定能力合同 |
| 新增远程频道 | Channel Gateway 合同和模拟 E2E 已完成；官方 API/权限/审核条件已重新核实；用户明确当前优先频道 |
| Windows 服务 | 托盘 Gateway 无法满足开机自启或无人值守需求，并有明确运维/升级方案 |
| 云同步/多用户 | 产品范围被用户明确改变，并重新完成隐私与权限设计 |

## 10. 下一入口

Phase 0 合并并完成公开仓库保护后，下一切片固定为 **P1.1 版本和制品身份**。在此之前不发布安装包，也不把源码或 CI 通过描述为可安装产品已经验收。

进入 P1.1 后仍按切片推进：在版本、制品身份和四层验收闭环前，不把开发打包描述为已发布产品，也不提前开始跨仓库共享核心抽取。

## 1. 本轮重新排序的依据

当前处于原型搭建阶段，优先回答三个问题：用户能否顺利开始查询，能否看懂并操作结果，是否愿意继续使用。先用真实使用流程验证这些问题，再按需要补安装发布和更大范围的架构统一。

2026-08-29 版计划把安装验收设为原生交互的前置，并将跨仓库共享核心和多频道网关纳入近期主线，前置工作过多。2026-09-03 按维护者明确的原型目标调整：

| 原安排 | 本次处理 | 原因 |
|---|---|---|
| P1.1 版本、哈希、安装制品先行 | 移到需要分发原型时 | 目前可以通过开发启动试用，不必先做发布系统 |
| P1.2 每个切片都对照四层验收 | 改为按改动范围验证；完整安装验收用于发布 | UI 迭代首先需要实际交互证据 |
| P1.3 原生交互行情卡 | 提到下一步，拆成 D1a / D1b | 直接补齐 Agent 问价到使用结果的流程 |
| P2.1 / P2.2 跨仓库共享核心 | 延后到桌面流程稳定、实际需要双宿主消费时 | 现有 Companion packages 足够支撑原型 |
| P2.4 Channel Gateway | 暂不排期 | 目前优先桌面，现有 QQ/OpenClaw 继续独立使用 |
| 全面故障矩阵、兼容窗口、迁移材料 | 在涉及对应数据源、公开制品或生产状态时使用 | 不把未来工作的要求套到每次页面修改上 |

已有只读边界、凭据保护、Electron 隔离和测试保留。调整的是新增工作的顺序与规模，不通过拆除已有保护来提速。

同日按维护者补充要求修订：功能对齐从现在进入主线。D1 打通第一条完整桌面流程后，直接逐项接入已有助手能力；界面和模型使用优化随功能推进。共享核心重构、安装发布仍按需要安排。

## 2. 当前代码具备什么、缺什么

本轮依据 `apps/desktop/src/renderer/App.tsx`、主进程/preload 和 `packages/agent-runtime/src/index.ts` 阅读确认；没有把源码阅读写成实机验收。

| 范围 | 已有能力 | 原型缺口 |
|---|---|---|
| 总览中的市场快捷查询 | 查询表单、买卖订单、成交统计、来源/时间和错误显示 | D1b/D2b0/D1c 已完成主管验收；真实 Warframe.Market 字段仍待实测 |
| Agent | D1a 已接共享行情卡；D1b/D2b0/D1c 已完成交互、一次范围与模板对齐；展示结果由桌面专用事件传递，runtime 仍只有脱敏摘要 | 其他工具原生结果按后续功能接入 |
| 页面状态 | D1a 已保留已访问页面、当前会话与结果；切页可继续查询并返回停止 | 仅本次应用运行内保留，不包含重启后的历史恢复 |
| 模型配置 | 已有 profile 保存、选择、健康检查和 OpenAI-compatible adapter | 配置与诊断已移到设置，主界面按实际模型显示说明；尚无真实远程模型桌面验收 |
| 掉落 | `drops.search` 服务、公共缓存、Agent 工具接入 | 缺少便于浏览的原生掉落结果与独立查询入口 |
| 工程 | 根级测试、41 条合成评估、Windows/Node 22 CI、开发打包 | 安装包和发布仍未验收；暂不作为原型 UI 的前置任务 |
| 个人数据 | `account.snapshot` 权限与脱敏尖峰 | 未接真实本机数据服务，不列作当前可用功能 |

P0.1～P0.3 已完成，候选能力已进入主线。无需重新建设 CI 或重做候选分支审查。

## 3. 功能对齐与执行顺序

顺序为 **D0 范围核对 → D1 市场完整流程 → D3 掉落/遗物 → D4 世界状态/周常/商店 → D5 个人数据与决策 → D6 愿望单/订阅**。D2 是随各功能推进的使用体验工作，不是 D3 及之后的前置阶段。每次实现一个能用的子切片，不等某个大模块全部完成才展示或试用。

### D1：Agent 中直接使用行情结果（原 P1.3）

状态：D1a、D1b、D2b0、D1c 均已完成主管验收。当前合成根测试 148 项、桌面打包与可见 Electron 39/39 通过；真实 Warframe.Market 尚未实测。

用户流程：问某物品的价格 → 看到行情卡 → 筛选订单 → 选择卖家 → 预览并复制购买私聊文本。

**D1a：先把行情卡接进对话。**

- 从现有市场页抽出共享 `MarketResultCard`，由市场页和 Agent 对话共同使用；成功、空订单和查询失败沿用现有语义。
- 从本次已完成的工具调用传递类型化展示结果到桌面，关联对应请求与会话；不为显示卡片再查一次市场，也不从模型文本解析订单。
- 展示数据保留在桌面当前会话内，模型与 trace 继续使用原有脱敏摘要；无需搭建通用 UI 插件或事件总线。
- 修复切换页面导致结果/会话丢失的问题，明确运行中切页、停止和完成后的监听清理。只需本次应用运行内保留，不建设历史数据库。

完成标准：用本地规则 profile 发起一次真实只读问价，对话内展示与市场页相同的行情卡；切去市场页再回来仍能看到结果。运行中切页不会遗留重复任务或监听，失败结果能理解并重试。

2026-09-03 验证：根级 build 与 85 项测试通过，确定性 eval 报告无漂移（reference 41/41，desktop/mock 各 40/41）；Electron 合成窗口验证查询复用、切页保留、隐藏时完成、返回取消、晚到结果丢弃、窗口监听清理、失败重试和空订单。真实本地规则查询“古纪V3”成功显示行情、来源与时间，切页后仍可见。仅开发打包与本机试用，未发布安装包或验收真实远程模型。

**D1b：补上订单操作。**

- 对话保留简洁摘要，订单操作集中在按需展开的详情区。在当前订单快照内分页，提供买卖方向和在线状态筛选，显示数量与快照时间。
- 卖单提供购买私聊预览及显式复制，反馈复制成功或失败；仅写入用户剪贴板，不自动发送。
- 按现有结果时间判断过期，过期后要求刷新再复制；刷新后让用户重新选择订单。
- 翻页、筛选与复制直接使用已校验结果，不调用模型；只增加完成这些交互所需的 IPC。

完成标准：用户能从一条 Agent 查询完成筛选、预览和复制；用合成订单检查过期、刷新后重选、复制失败和键盘操作。

- 每接入一个功能就补入口、示例与适用的下一步操作；先让当前会话记住明确查询实体，支持“这个多少钱 / 去哪里刷”等追问，按 D2b2 保存可清空的本地聊天/结果，不建设无依据的隐式用户画像。

完成标准：从打开应用到完成查询有清楚入口，设置不遮住主要内容，远程模型不再被标作免费离线后端。已配置模型完成一次桌面试用；若没有可用模型配置，明确留下这一项待试，不阻塞 D3。

完成标准：对应 D0 子项能在桌面回答“今天刷什么 / 目标在哪个当前奖池 / 本周有什么”，空结果与来源失败可区分。逐项交付，无需一次完成全部情报。

### D5：个人库存、周常记录与个人决策对齐

状态：待开发，按实际接入分小切片。

- D5a 接真实本机只读快照，先做账号概览、库存/遗物/赋能查询与快照时间，再提供账号周常证据。
- 接周常手动记录与有证据支持的完成状态，以及商店已购/已拥有标记；只修改助手自己的记录，不修改游戏账号。
- D5b 起逐项加入库存配裂缝、开遗物、精炼、杜卡德方案与奸商建议，补齐 D3/D4 的个人增强；紫卡详情/估价另做一个切片。
- WFInfo 联动另列子项，保留独立组件，只对接用户可用的结果与状态。

完成标准：用户能查到匹配范围和时间的个人数据，并据此完成对应选择；未接数据、数据过旧与确实未拥有清楚区分。现有记录如需迁入，才执行 §5 的迁移步骤。

### D6：愿望单与订阅提醒对齐

状态：待开发，已纳入功能主线。

- D6a 先做愿望单列表及管理，再接当前合价单检查和后续命中的桌面提醒。
- D6b 从裂缝/仲裁等已接数据的订阅开始，逐类补齐目录中的事件、商品/轮换与个人掉落提醒，支持查看、暂停、恢复和取消。
- 按产品行为合同一并交付提醒记录、Windows通知开关和托盘生命周期；仅明确订阅可通知，实际退出停止监测。QQ 继续由原系统负责，不要求先做新频道网关。

完成标准：用户能创建、修改或停用条件，并在条件命中时收到一次可解释的桌面提醒；按类型记录覆盖情况，不用一个订阅样例代表全部功能对齐。接管既有状态时执行 §5，避免两端重复写入或投递。

## 4. 延后工作的进入条件

| 工作 | 何时做 | 届时的最小范围 |
|---|---|---|
| 安装与预发布（原 P1.1 / P1.2 / P1.4） | 要把原型交给另一台电脑或其他人试用 | 一致版本、构建提交与时间、安装制品和校验值、安装/启动/卸载；已有安装需验证升级保留数据 |
| Release 自动化 | 已有重复发布需求 | 从验证过的提交产出带已知限制的预发布；签名与自动更新另按需要评估 |
| 跨宿主共享核心（原 P2.1 / P2.2） | 桌面业务基本稳定，需要 Companion 与 OpenClaw 共用实现 | 先选 Market，确认语义差异，使用有版本的 package，验证后逐宿主切换 |
| QQ bridge / 新频道（原 P2.4） | 明确要从新频道使用桌面 Agent | 只接一个真实频道及它需要的身份、连接、回执；再提取有重复需求的公共 adapter |
| 通用 Outbox / 多频道投递平台 | D6 的桌面提醒确有超出本地实现的需求 | 先完成具体提醒；重复投递逻辑出现后再抽象，D6 本身不后移 |
| SQLite、RAG、复杂模型路由、MCP、Windows 服务 | 现有实现出现明确瓶颈或真实消费者 | 解决观察到的问题，不预设必须补齐技术栈 |

本机遇到打包问题可以随时做一次 `make` 定位，但不因此自动开启整条发布工程。跨仓库暂存的重复实现不是原型阻塞项，也不宣称已经完成统一。

## 5. 保留的实现边界

原型沿用 Electron/React、现有 packages 和 Agent Harness。功能页与 Agent 共用服务和结果组件；按实际复用抽取模块。

- Warframe、AlecaFrame、WFInfo、Market 和账号集成只读，不操作游戏、交易、聊天或账号资产。
- 凭据继续走现有引用机制；测试、截图、日志和公开文档不含密钥、账号标识、原始个人快照或真实聊天。个人数据接入仍保留可信身份与白名单投影。
- 用户看到的事实来自工具，保留来源、时间与查询范围，区分无结果和数据源失败。模型不得自行生成事实或权限。
- 不直接依赖已部署 OpenClaw 目录、深层源码路径或 CLI 输出。目标架构见 [`ARCHITECTURE.md`](ARCHITECTURE.md)，它不要求原型提前实现所有模块。
- 当真正替换生产状态写入者时，才执行备份、只读对比、停旧写者、迁移、验证和可回滚步骤；始终只有一个写入者，不删除用户数据。普通 UI 状态保留不等同于生产状态迁移。

## 6. 原型切片的完成标准

1. 说明这次改善的用户流程，做到可以操作或展示。
2. UI 变化实际启动或渲染并走通该流程，重点看加载、空结果、失败/重试；涉及复制和任务生命周期时验证对应分支。
3. 从根运行现有 `npm test`；新增测试集中在本次改变的行为。涉及构建、工具/事实或安装时，分别执行相关 build、eval 或 `make`。现有 CI 保持，不另加与切片无关的门禁。
4. 更新 D0 对照表、直接相关的使用说明和当前状态；功能对齐至少有一条对应旧能力的桌面使用流程。记录哪些已实现、哪些未试；仅有计划不能记作功能完成。

源码、CI、安装包和真实模型试用各自报告实际结果。安装/发布的详细验收见 [`ACCEPTANCE.md`](ACCEPTANCE.md)，不要求每个原型切片都完成四层。

评估沿用现有合成用例，业务事实投影保持与生产一致；真实模型试用只回答本次功能是否可用，不默认跑完整付费评估。保留现有 trace，不为普通 UI 修改扩建追踪平台。
